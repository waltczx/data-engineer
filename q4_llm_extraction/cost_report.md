# Q4 成本报告

## 实际花费

| 来源 | 金额 |
|---|---|
| **DeepSeek 账单（2026-11-26，全部运行合计）** | **¥7.76** |
| 按 1 美元 ≈ 6.8–6.9 元换算 | 约 $1.13–1.15 |
| 程序按 API 返回的 usage 自行累计（`cost_ledger.jsonl`） | $1.150 |
| 预算 | $3.00 |

程序记录与账单相差在 2% 以内，所以下文的 token 和成本拆分可以直接采用程序记录。

各次运行（`cost_ledger.jsonl`）：

| 运行 | 请求数 | 输入 token | 输出 token | 费用 |
|---|---|---|---|---|
| 试跑（`--limit 20`） | 1 | 3,232 | 1,869 | $0.0016 |
| 全量 | 683 | 2,069,048 | 1,371,824 | $1.1335 |
| 实验：单条请求（40 条） | 40 | 58,056 | 4,204 | $0.0112 |
| 实验：批量请求（40 条） | 2 | 5,874 | 4,167 | $0.0034 |
| **合计** | **726** | **2,136,210** | **1,382,064** | **$1.1497** |

全部请求都在非高峰时段（半价）发出。模型 `deepseek-flash`，关闭思考模式。全量运行 152 秒（题目上限 40 分钟），683 次请求无失败，只有 1 次网络中断后自动重试成功。

## 单条平均成本（全量运行）

| 口径 | 条数 | 平均每条 |
|---|---|---|
| 走模型的评价 | 13,765 | $0.000082（每千条约 $0.08） |
| 有文本的评价（含规则） | 14,460 | $0.000078 |
| 全部评分 ≤3 的评价（含无文本） | 22,493 | $0.000050 |

每次请求平均 20 条评价，输入约 3,030 token、输出约 2,010 token，折合**每条评价输入约 150 token、输出约 100 token**。

## 钱花在哪里

| 部分 | token | 单价（非高峰） | 费用 | 占比 |
|---|---|---|---|---|
| 输入 | 2,069,048 | $0.15 / 百万 | $0.310 | 27% |
| 输出 | 1,371,824 | $0.60 / 百万 | $0.823 | 73% |

**输出占了近四分之三。** 输出单价是输入的 4 倍，而每条结果包含原文引文、英文翻译和几个数值字段。要继续降本，首先应该压缩输出，比如让模型返回引文在原文中的起止位置而不是复制引文，或者把英文翻译改为按需生成。

## 单条请求 vs 批量请求（`batch_experiment.json`）

同样 40 条评价，分别逐条请求和每批 20 条请求：

| 方式 | 请求数 | 每条输入 token | 每条输出 token | 每条成本 |
|---|---|---|---|---|
| 单条 | 40 | 1,451 | 105 | $0.000281 |
| 批量（20 条一批） | 2 | 147 | 104 | $0.000085 |

批量每条成本是单条的 **1/3.3**。差别全部来自输入：约 1,380 token 的 system prompt（含 few-shot 示例）单条时每条付一次，批量时 20 条分摊；输出量两种方式几乎一样。代价是一致性：两种方式类别完全相同的占 82.5%（见 `accuracy_evaluation.md`）。

按全量 13,666 次唯一文本推算，如果全部单条请求，费用约 $3.84，会超出预算。

## 预估与实际的差异

| 项目 | 运行前预估（`--dry-run`） | 实际 | 偏差 |
|---|---|---|---|
| 输入 token | 563,978 | 2,069,048 | 低估 3.7 倍 |
| 输出 token | 1,503,260 | 1,371,824 | 高估 9% |
| 费用（非高峰） | $0.986 | $1.133 | 低估 15% |

预估按"每 3.5 个字符约 1 个 token"估算 system prompt，实际上英文 prompt 加 JSON 示例的 token 数比这个多得多。好在输出才是大头，而输出估得比较准，所以总费用只差了 15%。以后应该先发一次真实请求，用返回的 usage 校准，再做全量预估。

## 没有解决的问题：缓存没有生效

设计时预期：DeepSeek 对相同的 prompt 前缀自动缓存，命中部分按 $0.003 / 百万 token 计费，相当于原价的 2%。但 726 次请求返回的缓存命中 token 全部是 0，账单金额也与"全部按未命中计费"的结果一致。这说明确实没有命中缓存，而不只是程序没统计到。连续顺序发出的 40 次单条请求同样没有命中，所以也不是并发导致的。

如果缓存生效，约 1,380 token 的 system prompt 只在第一次按原价计费，全量费用约为 **$1.00**（节省约 12%）。节省有限，同样是因为成本的大头在输出。原因暂未查明；`check_usage_fields.py` 会连续发送两次相同请求并打印原始 usage，可用于进一步排查。

## 如果放到高峰时段运行

同样的 token 量按高峰价计算约 **$2.27**，仍在预算内，但余量只有 $0.73。所以全量运行特意安排在非高峰时段（北京时间 18:00 至次日 09:00，以及周末）。
