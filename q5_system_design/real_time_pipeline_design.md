# Q5.1 - 实时数据管道设计

## 📋 题目背景

Olist 当前的数据是离线 CSV 导出。现在业务需求是——卖家希望**实时**看到自己的订单情况、买家评价、物流异常。

请设计一个**实时数据架构**，满足：

- 订单状态变更后 **30 秒内** 反映在卖家后台
- 评价文本进来后 **1 分钟内** 触发情感分析 + LLM 抽取
- 物流异常（如某订单延迟超过预计时间）**自动报警**到卖家
- 历史数据查询（卖家想看过去 6 个月的成交曲线）**毫秒级响应**
- 当前数据规模：**10 万订单/天**，预计 2 年内增长到 **100 万订单/天**

要求：800-1500 字 + 一张架构图

---

先算规模（比例取自 Olist 数据）：

| 指标 | 10 万单/天 | 100 万单/天 |
|---|---|---|
| 订单状态事件（每单约 4 个） | 约 5 条/秒 | 约 50 条/秒 |
| 高峰（2017 年黑五是日均的 6.2 倍） | 约 30 条/秒 | 约 300 条/秒 |
| 有正文的评价（41%） | 4.1 万/天 | 41 万/天 |
| ≤3 星且有正文（14.6%） | 1.5 万/天 | 15 万/天 |

**结论**：即使到 100 万单/天，吞吐量也不大。难点在于正确性（事件乱序和重复）、时效承诺，以及 LLM 的成本和可靠性。

## 1. 整体架构图

> 用 ASCII art、Mermaid 或附图均可

```
 业务服务 ──写入──> MySQL 主库（OLTP，事实来源）
                        │ binlog
                        ▼
                 CDC（Canal / Debezium）
                        ▼
      Kafka：order_events / review_events / shipment_events
     ┌──────────────────┬┴─────────────────┬─────────────────┐
     ▼                  ▼                  ▼                 ▼
 ① 订单状态聚合      ② 评价路由          ③ 物流时效监控      ④ 入仓
 去重，按卖家汇总   去重→规则→微批      每单一个截止定时器   写 OLAP 明细
     │                  │                  │ 到期未签收
     ▼                  ▼                  ▼
 Redis 实时看板     LLM Worker ──> LLM API  告警服务（合并/限流）
     │              （引文校验）           ──> 站内信 / 邮件
     ▼                  ▼
 卖家后台 API ──> Redis（热点） / OLAP（ClickHouse/Doris：明细 + 卖家日汇总）
                                   ▲ 每晚与 MySQL 全量对账
```

- **状态 30 秒内可见**：CDC 延迟为秒级，①按 `order_id` 保留最新状态并更新 Redis 计数，端到端 5 到 10 秒。
- **评价 1 分钟内抽取**：②按"满 20 条或等满 20 秒"微批。100 万单/天时 ≤3 星有正文约 1.7 条/秒，攒满约 12 秒，加上调用约 5 秒（Q4 实测）。
- **6 个月曲线毫秒级**：按"卖家 × 天"预聚合，3,000 卖家 × 180 天只有 54 万行。

## 2. 数据存储选型

> 哪些数据进 OLTP、哪些进 OLAP、哪些进消息队列、哪些进缓存？为什么？

| 存储 | 放什么 | 为什么 |
|---|---|---|
| MySQL | 订单、支付、评价原文 | 写入需要事务。**不承担分析查询**：Q2.4 实测数据增长 10 倍后，一个汇总查询从 0.5 秒变为 13 秒。 |
| Kafka | 变更事件、LLM 结果 | 解耦多个消费者；缓冲黑五高峰；**可重放**：prompt 改版后重放评价重新抽取。 |
| Redis | 卖家实时计数、最近订单 | 小、热、可从 OLAP 重建。 |
| OLAP | 明细、抽取结果、日汇总 | 列存储适合扫描加聚合。100 万单/天时，一年约 4 亿行商品明细。 |

## 3. LLM 部分如何避免成本失控

> 100 万订单/天，如果每条评价都过 LLM，年成本估算多少？怎么优化？

按 Q4 实测单价（`deepseek-flash` 非高峰价，高峰价为两倍）：

| 方案 | 每天调用 | 单条成本 | 年成本 |
|---|---|---|---|
| A. 每条评价单独调用 | 100 万 | $0.000281 | **约 10.3 万美元** |
| B. 只处理有正文的，每批 20 条 | 41 万 | $0.000082 | 约 1.2 万美元 |
| C. B 中只对 ≤3 星做抽取 | 15 万 | $0.000082 | **约 4,400 美元** |

从 A 到 C 降低 96%。具体做法：没有正文的不调用；批量处理让 system prompt 由 20 条分摊；4、5 星只用规则或小模型判断情感；相同文本去重。Q4 中 73% 的费用是输出，改为返回引文在原文中的位置，还能再省约三分之一。另外设每日预算熔断，超过上限就降级为纯规则处理。

模型单价本身是最大的成本杠杆。到 100 万单/天时，可以用积累的结果训练小模型，LLM 只处理小模型拿不准的部分。

## 4. 三个最大的风险点和应对方式

### 风险 1：事件乱序或重复，卖家看到错误状态

**说明**：CDC 是"至少投递一次"。数据本身也有矛盾：8 个已送达订单没有送达时间，6 个已取消订单却有送达时间；814 个 `review_id` 对应多个订单。

**应对**：按 `order_id` 分区保证有序；用"`order_id` + binlog 位点"做幂等更新；状态机拦截非法跳转，记入异常表；每晚与 MySQL 对账。

### 风险 2：LLM 故障、限流或成本突变

**说明**：外部 LLM 是唯一不受控、延迟波动最大的组件。

**应对**：评价先进 Kafka，LLM 故障时只积压不丢失；超时重试，连续失败就熔断并降级为规则处理，保证情感判断仍在 1 分钟内给出；准备第二家供应商；输出做 schema 和引文校验，防止编造的问题推给卖家。

### 风险 3：物流告警误报，或短时间内告警过多

**说明**：预计送达时间只有日期（全部是 00:00），直接按时间戳比较会把当天送达的订单误判为延迟。延迟率 6.8%，100 万单/天时每天约 6.8 万单；某家物流商出故障时，一个卖家可能被告警淹没。

**应对**：截止时间设为预计送达日当地时间的 23:59，用 Flink 按订单注册定时器，签收时取消；告警按卖家合并成摘要；同一物流商的超期订单激增时，升级为平台级事件统一通知。另外，付款后迟迟没有交给物流商时提前预警，此时卖家还来得及处理。

## 5. 关于业务规模变化的考虑

> 10 万订单/天 vs 100 万订单/天，架构会有什么不同？

- **10 万单/天**：不上 Flink 和 OLAP。Canal 接 Kafka，一个 Python 消费服务维护 Redis 看板和 MySQL 副本上的日汇总表；物流告警每 15 分钟用索引扫描一次；LLM 用异步队列加 2 到 3 个 worker。一两个人就能维护。
- **100 万单/天**：升级的原因不是吞吐量，而是上千万个未签收订单的定时器状态和精确一次语义（交给 Flink），以及数据超出内存后 MySQL 上的聚合变慢（换 OLAP）。Kafka 从一开始就保留，所以上游不用改动，可以逐个模块替换。

**局限**：成本只计算了 LLM，没有算基础设施；评价原文涉及个人信息，需要符合巴西的个人数据保护法（LGPD），本文未展开；Q4 中模型路线的抽取准确率约 80%，推送给卖家之前，应先在内部运行一段时间、评估误报率。
